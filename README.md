# Двухстадийная рекомендательная система (Retrieval → Ranking)

Рекомендации для карточек товаров / ленты в e-commerce на событиях `view → addtocart → transaction`
(формат датасета [RetailRocket](https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset)).

> **Честная оговорка.** Цифры ниже получены на **синтетических данных в формате RetailRocket**
> (генератор — `recsys/data.py`), потому что в среде, где я собирал проект, не было доступа в интернет.
> Код сам переключается на настоящий датасет: положите `events.csv` и `item_properties_part{1,2}.csv`
> в `data/retailrocket/` и запустите `python run.py`. Абсолютные числа на реальных данных будут другими
> (там выше разреженность и шум); ценность этой работы — в архитектуре и методологии оценки.

```bash
pip install -r requirements.txt
python run.py                 # синтетика, ~45 сек на 1 CPU
python run.py --data data/retailrocket   # настоящий RetailRocket
```

Бэкенды выбираются автоматически: retrieval — `implicit.ALS` (если установлен, иначе собственный ALS на numpy),
ранкер — `CatBoostRanker(YetiRank)` → `LGBMRanker(lambdarank)` → `HistGradientBoosting` (sklearn).
**Прогон, по которому получены цифры, шёл на запасных вариантах** (numpy-ALS + sklearn-GBDT), т.к. `implicit`,
`catboost`, `lightgbm` не были установлены. Ветки `implicit`/`CatBoost`/`LightGBM` написаны, но мной не запускались.

## Архитектура и почему именно такая

```
каталог (тысячи…миллионы)
   │  Stage 1: RETRIEVAL  — дёшево, высокий recall, ~50 кандидатов/пользователь
   │    • ALS (40)       персональный источник: скалярное произведение векторов user·item
   │    • Fresh (10)     новые товары в любимых категориях  → cold start товаров
   │    • Trend (добивка) популярное за 7 дней             → cold start пользователей
   ▼
50 кандидатов
   │  Stage 2: RANKING  — дорого на один объект, высокая точность, богатые фичи
   │    • GBDT-ранкер, 20 фич пары (user, item, контекст)
   ▼
top-10 в выдачу
```

**Почему две стадии, а не одна модель.** Тяжёлую модель с кросс-фичами нельзя посчитать на всём каталоге
(N_users × N_items). Поэтому первая стадия обязана быть «двухбашенной»: векторы пользователя и товара
считаются независимо, поиск кандидатов = top-K по скалярному произведению (на проде — ANN-индекс вроде FAISS/HNSW;
здесь — точный матричный `U @ Iᵀ`, концептуально то же самое). Вторая стадия видит только 50 объектов и может
позволить себе фичи взаимодействия (похожесть на последние просмотры, доля категории в истории, цена относительно
средней у пользователя) и обучение под ранжирующий лосс.

**Почему ALS в retrieval.** Данные — неявная обратная связь (нет оценок, есть факт события). ALS по Hu–Koren–Volinsky
моделирует «предпочтение» `p=1[r>0]` с уверенностью `c = 1 + α·log1p(r)`, где `r` — сумма весов событий
(view=1, cart=3, buy=5). Логарифм гасит эффект ботов/накруток просмотров. Это быстрая, хорошо изученная база,
которая выдаёт именно то, что нужно retrieval: векторы для ANN.

**Почему GBDT-ранкер.** Табличные фичи разной природы + пропуски (холодные) + нелинейные взаимодействия;
GBDT обрабатывает пропуски нативно и обучается за секунды-минуты. Ранжирующий лосс (YetiRank/LambdaRank)
оптимизирует порядок внутри группы (пользователя), а не абсолютную вероятность.

## Холодный старт

| Кто холодный | Что происходит | Что делаем |
|---|---|---|
| **Пользователь без истории** (6% тестовых) | у ALS нет вектора → `als_score = NaN` | кандидаты: 20 fresh + тренд; ранкер видит `u_n_events=0` и опирается на популярность/тренд |
| **Товар без/с малой историей** (<3 событий) | вектор ALS ненадёжен → исключён из ALS-выдачи | отдельный источник *Fresh* (появился ≤7 дней назад), скоринг = `log(1+популярность7д) + 3·доля_категории_пользователя` |
| **Сглаживание в ранкере** | у новых товаров статистика конверсий шумная | `cart_rate = (carts+0.1)/(views+10)`, фича `item_age_d` позволяет ранкеру самому решить, сколько доверять новизне |

Чего тут нет, но на проде нужно: content-эмбеддинги товаров (текст/картинка) для настоящего cold-start retrieval,
exploration (bandit) для сбора данных по новым товарам, онбординг-опрос для новых пользователей.

## Как оценивалось качество (и как избегал утечек)

* **Временной сплит, а не случайный.** `Snapshot(T)` строится только из событий `< T`. Тест: последние 14 дней.
  Ранкер учится на двух предыдущих 14-дневных окнах: для каждого окна retrieval переобучен на истории до его начала,
  фичи считаются «как на момент показа», метки — из окна. Так ранкер видит ровно то распределение ALS-скоров,
  что и в проде (ALS **не** обучался на метках — иначе ранкер выучил бы «доверяй ALS слишком сильно»).
* **Позитив** = пользователь взаимодействовал с товаром в окне, которого не было в его истории,
  и товар уже существовал в каталоге на момент T. Уже виденное не рекомендуем (для e-com с повторными покупками
  это отдельная задача — repurchase).
* **Метрики** @K на пользователях, у которых в окне есть хотя бы один позитив:
  * `Recall@K` — какую долю реально интересного нашли (знаменатель — ВСЕ позитивы, а не только попавшие в кандидаты);
  * `NDCG@K` — то же с учётом позиции; `HitRate@K` — доля пользователей, у которых угадан хотя бы один;
  * `Recall@50` retrieval-стадии = **потолок** для ранкера: он не может вернуть то, что retrieval не принёс;
  * `Coverage@10` — доля каталога, показываемая хоть кому-то (защита от вырождения в «всем одно и то же»).
* **Сравнение** с бейзлайнами на одних и тех же пользователях: глобальный тренд за 7 дней; порядок retrieval без ранкера.

## Результаты (синтетика, seed 0; 5146 тестовых пользователей)

| Система | Recall@10 | HitRate@10 | NDCG@10 | Coverage@10 |
|---|---|---|---|---|
| Популярное за 7 дней | 0.036 | 0.113 | 0.025 | 1.0% |
| Retrieval (ALS+fresh+trend), без ранкера | 0.117 | 0.316 | 0.088 | 30.8% |
| **Retrieval + ranker** | **0.142** | **0.376** | **0.108** | 26.0% |

Потолок retrieval: **Recall@50 = 0.284**, HitRate@50 = 0.593.
Ранкер дал **+21% Recall@10 / +22% NDCG@10** над порядком retrieval (на втором сиде: NDCG@10 0.085 → 0.104, +22%).
Одна синтетика и 2 сида — это не доверительный интервал; на реальных данных нужен bootstrap по пользователям.

**Сегменты.** Тёплые пользователи (4825): NDCG@10 0.094 → 0.112. Холодные (321): ранкер = популярность (0.047 против 0.048):
он правильно понял, что без истории лучший сигнал — тренд, и выправил порядок (retrieval-порядок давал свежие товары
первыми и проигрывал: 0.010). Персонализации для холодных нет, и честно её не появляется — для неё нужен контент или онбординг.

**Что выучил ранкер** (permutation importance, падение NDCG@10): популярность за 7 дней (0.030), доля категории в истории
пользователя (0.020), возраст товара (0.013), `als_score` (0.009), ранг ALS (0.007). То есть ALS — лишь один из сигналов;
основной прирост — от фич, которых в матричной факторизации нет (свежесть/тренд, категориальная аффинность).

## Ограничения и что видно в результатах

* **Ранкер сужает выдачу:** покрытие падает 30.8% → 26.0%, он тянется к трендовым товарам. На проде это лечится
  диверсификацией (MMR), квотой на exploration, штрафом за популярность; здесь не делалось.
* **Fresh-кандидаты ранкер почти не берёт** (1.5% top-10 при 21% среди кандидатов): их hit-rate 0.76% против 2.5% у ALS.
  Это выбор модели по метрике «следующие 14 дней», но не обязательно бизнес-оптимум (новые товары нужны для роста каталога).
* Данные синтетические: структура вкусов в них задана мной, поэтому ALS работает «слишком хорошо».
  Не сравнивайте абсолютные числа с RetailRocket.
* Нет онлайн-оценки: офлайн-NDCG коррелирует с CTR, но не равен ему (position bias в логах — отдельная тема).
* Retrieval считает точный `U @ Iᵀ` блоками; для миллионов товаров нужен ANN (FAISS/ScaNN).

## Структура

```
recsys/data.py       загрузка RetailRocket / синтетический генератор
recsys/snapshot.py   срез знаний на момент T (без утечек): матрица взаимодействий, статистики
recsys/retrieval.py  ALS + fresh + trend → 50 кандидатов
recsys/features.py   фичи пары (user,item), метки из будущего окна
recsys/ranking.py    CatBoostRanker / LGBMRanker / sklearn-GBDT
recsys/metrics.py    Recall/HitRate/NDCG@K
run.py               весь пайплайн + бейзлайны + сегменты + importance → results/
```

## Идеи для следующих шагов
Мульти-источниковый retrieval (item-item co-visitation, two-tower на PyTorch + FAISS), recall по каждому источнику
отдельно, обучение ранкера с градуированной релевантностью (view/cart/buy как 1/2/3), time-decay событий, калибровка
и онлайн A/B.
